# Контакты клиента и напоминания о подписках

В админке «Клиенты» доступны электронный адрес, Telegram, Max и основной канал.
Email хранится в существующем `User.email`, отдельная копия не создаётся.
Изменение email здесь меняет контакт для писем/платежей, но не `User.username`
(логин существующего пользователя). Telegram — положительный числовой chat_id личного чата, Max — положительный
числовой user_id, не @username, телефон или токен бота. Старые Telegram
username сохраняются, но выбрать их основным каналом до указания ID нельзя.
Основной канал по умолчанию — email. Нельзя выбрать пустой контакт или очистить
контакт выбранного канала. Старые записи без email потребуют заполнения контакта
при редактировании; миграция не придумывает отсутствующие адреса.

## Развёртывание

1. Применить миграцию `python manage.py migrate` обычной процедурой развёртывания.
2. SMTP по умолчанию: `smtp.yandex.ru`, SSL, порт 465, пользователь и отправитель
   `info@karion24.ru`. `EMAIL_USE_TLS=0`, `EMAIL_USE_SSL=1`.
   Пароль приложения Яндекса задаётся только в защищённой переменной
   `EMAIL_HOST_PASSWORD`; в репозитории его нет. Настройки можно переопределить
   через `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `DEFAULT_FROM_EMAIL`.
3. При необходимости задать `KARION_CABINET_URL` (по умолчанию
   `https://lk.karion24.ru/cabinet/`).
4. Проверить выборку: `python manage.py send_subscription_reminders`.
   Без `--apply` письма не отправляются и записи уведомлений не создаются.
5. Добавить в существующий планировщик запуск каждые 10 минут из каталога проекта:
   `python manage.py send_subscription_reminders --apply`.
   Например, для существующего развёртывания в `/opt/karion-portal`:
   `*/10 * * * * cd /opt/karion-portal && /opt/karion-portal/venv/bin/python manage.py send_subscription_reminders --apply`.
   Пользователь планировщика должен иметь настройки приложения и доступ к БД.

Уведомляется каждая активная подписка активного клиента/пользователя отдельно,
когда `now < Subscription.expires_at <= now + 24 часа`. Текст содержит название,
номер подключения и реальную дату окончания из Subscription в часовом поясе Django.
После продления напоминание возможно снова для новой даты окончания.
Заказы, сроки, статусы подписок и Remnawave команда не меняет.
Если планировщик не работал всё последнее 24-часовое окно, истёкшей подписке
запоздалое напоминание не отправляется.

## Telegram и Max: подключение существующих шлюзов

Реализованы адаптеры `portal.notification_backends.send_telegram` и `send_max`
по контрактам `integrations/telegram/services.py` и `integrations/max/services.py`
из предоставленного dash.zip. Код тикетов, вебхуки и настройки другого проекта
не импортируются. Подсказки в админке показывают требуемый формат ID.

Telegram поддерживает два варианта:

- существующий шлюз: `TELEGRAM_BOT_SERVER_URL` (HTTPS) и защищённая
  `TELEGRAM_BOT_SERVER_TOKEN`. Запрос `POST /send-message`, JSON
  `{"chat_id": 123, "text": "…"}`, заголовок `X-KARION-TOKEN`;
- напрямую: при пустом `TELEGRAM_BOT_SERVER_URL` используется защищённая
  `TELEGRAM_BOT_TOKEN`, Telegram Bot API `sendMessage`.

MAX: защищённая `MAX_BOT_TOKEN`; `POST https://platform-api.max.ru/messages`,
query-параметр `user_id`, JSON `{"text": "…"}`, токен в `Authorization`.
В ответе ожидается ID принятого сообщения. HTTP-ошибки, некорректный JSON,
редиректы и отрицательное подтверждение не считаются успешной отправкой.
Тексты ответов и токены не включаются в сообщения об ошибках.

Оба бота должны иметь право писать получателю. Telegram-пользователь должен
запустить именно того бота, которым выполняется отправка. Сам username не
позволяет определить chat_id. ID берутся из взаимодействия с существующим ботом
(в архиве они хранятся как telegram_chat_id и max_user_id).

Настройки окружения архива читаются через os.getenv; сам архив не содержит
runtime-значений токенов и адреса шлюза в изученных клиентах. Их нужно задать
на сервере. Отправка реальным клиентам при разработке не выполнялась.

При необходимости пути адаптеров можно переопределить через
`KARION_TELEGRAM_NOTIFICATION_BACKEND` / `KARION_MAX_NOTIFICATION_BACKEND`.
Контракт функции: `send(*, recipient, message, idempotency_key)`, исключение при
неподтверждённой отправке, нормальный возврат только после успеха.

## Повторные попытки и ограничения доставки

`SubscriptionReminder` хранит одну запись на пару подписка/дата окончания,
канал последней попытки, число попыток, время успеха и тип последней ошибки.
Контакт и тело ответа шлюза в журнал ошибок не записываются. После успешной
отправки повторный запуск для этой даты пропускается. Ошибки повторяются на
следующем запуске, пока подписка в 24-часовом окне. Ошибки и отсутствие профиля
дают ненулевой exit status, не останавливая обработку других подписок.

Команда использует Linux flock; `KARION_REMINDER_LOCK_FILE` по умолчанию
`/tmp/karion-subscription-reminders.lock`. Все локальные запуски должны использовать
один путь и пользователя. Запускать планировщик на одном сервере: файловая
блокировка не координирует независимые контейнеры/хосты.

SMTP и БД не составляют общую транзакцию. Если сообщение принято, но процесс
упал до записи успеха (или шлюз принял запрос, но ответ потерян), повтор возможен.
Строгую exactly-once доставку SMTP не гарантирует; у шлюзов в архиве не обнаружено контракта идемпотентности. Адаптеры получают
стабильный idempotency_key, но не добавляют недокументированных параметров
к запросам. При неопределённом результате запроса дубликат также возможен.
Продление непосредственно во время сетевой отправки может дать уже неактуальное
напоминание: дата перечитывается перед отправкой, но оплаченные дни не меняются.
