# Контакты клиента и напоминания о подписках

В админке «Клиенты» доступны электронный адрес, Telegram, Max и основной канал.
Email хранится в существующем `User.email`, отдельная копия не создаётся.
Изменение email здесь меняет контакт для писем/платежей, но не `User.username`
(логин существующего пользователя). Telegram — положительный числовой chat_id личного чата, Max — положительный
числовой user_id, не @username, телефон или токен бота. Старые Telegram
username сохраняются, но выбрать их основным каналом до указания ID нельзя.
Основной канал по умолчанию — email. Нельзя выбрать пустой контакт или очистить
контакт выбранного канала. Старые записи без email потребуют заполнения контакта
при редактировании; миграция не придумывает отсутствующие адреса.

## Развёртывание

1. Применить миграции 0026 и 0027 `python manage.py migrate` обычной процедурой развёртывания.
2. SMTP по умолчанию: `smtp.yandex.ru`, SSL, порт 465, пользователь и отправитель
   `info@karion24.ru`. `EMAIL_USE_TLS=0`, `EMAIL_USE_SSL=1`.
   Пароль приложения Яндекса задаётся только в защищённой переменной
   `EMAIL_HOST_PASSWORD`; в репозитории его нет. Настройки можно переопределить
   через `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `DEFAULT_FROM_EMAIL`.
3. При необходимости задать `KARION_CABINET_URL` (по умолчанию
   `https://lk.karion24.ru/cabinet/`).
4. Проверить выборку: `python manage.py send_subscription_reminders`.
   Без `--apply` письма не отправляются и записи уведомлений не создаются.
5. Добавить в существующий планировщик запуск каждые 10 минут из каталога проекта:
   `python manage.py send_subscription_reminders --apply`.
   Например, для существующего развёртывания в `/opt/karion-portal`:
   `*/10 * * * * cd /opt/karion-portal && /opt/karion-portal/venv/bin/python manage.py send_subscription_reminders --apply`.
   Пользователь планировщика должен иметь настройки приложения и доступ к БД.

Уведомляется каждая активная подписка активного клиента/пользователя отдельно,
когда `now < Subscription.expires_at <= now + 24 часа`. Текст содержит название,
номер подключения и реальную дату окончания из Subscription в часовом поясе Django.
После продления напоминание возможно снова для новой даты окончания.
Заказы, сроки, статусы подписок и Remnawave команда не меняет.
Если планировщик не работал всё последнее 24-часовое окно, истёкшей подписке
запоздалое напоминание не отправляется.

## Telegram и Max: подключение существующих шлюзов

Реализованы адаптеры `portal.notification_backends.send_telegram` и `send_max`
по клиентским реализациям `integrations/telegram/services.py` и `integrations/max/services.py`
из предоставленного dash.zip. Код тикетов, вебхуки и настройки другого проекта
не импортируются. Подсказки в админке показывают требуемый формат ID.

Telegram поддерживает два варианта:

- существующий шлюз: `TELEGRAM_BOT_SERVER_URL` (HTTPS) и защищённая
  `TELEGRAM_BOT_SERVER_TOKEN`. Запрос `POST /send-message`, JSON
  `{"chat_id": 123, "text": "…"}`, заголовок `X-KARION-TOKEN`.
  Это ожидания клиента из архива, не проверенный контракт серверного обработчика.
  Сервер `/send-message` в dash.zip отсутствует. До получения исходника либо
  обезличенного примера фактического ответа успешная семантика не подтверждена.
  Поэтому требуется `TELEGRAM_BOT_SERVER_RESPONSE_VALIDATOR` — путь к функции
  `validator(response)`, возвращающей строго True только для подтверждённого успеха.
  Без неё запрос НЕ отправляется. Если на сервере подтверждены HTTP 200 и
  `ok: true`, можно явно выбрать
  `portal.notification_backends.telegram_gateway_dash_response`.
  Для другого контракта нужен валидатор по фактической спецификации, не догадка.
  Неизвестный ответ после отправки блокирует автоматическое повторение;
- напрямую: при пустом `TELEGRAM_BOT_SERVER_URL` используется защищённая
  `TELEGRAM_BOT_TOKEN`, Telegram Bot API `sendMessage`.

MAX: защищённая `MAX_BOT_TOKEN`; `POST https://platform-api.max.ru/messages`,
query-параметр `user_id`, JSON `{"text": "…"}`, токен в `Authorization`.
Используется именно БОТ: архив читает MAX_BOT_TOKEN и обращается к бот-API.
Личный аккаунт, его сессия или пользовательский шлюз не используются и не
подменяются ботом. Если нужен другой механизм, требуется отдельное подтверждение.
Как в dash.zip, HTTP 2xx считается принятием: mid и даже JSON могут отсутствовать.
Прежнее обязательное требование mid удалено. Редиректы не выполняются.
Тексты ответов и токены не включаются в сообщения об ошибках.

Оба бота должны иметь право писать получателю. Telegram-пользователь должен
запустить именно того бота, которым выполняется отправка. Сам username не
позволяет определить chat_id. ID берутся из взаимодействия с существующим ботом
(в архиве они хранятся как telegram_chat_id и max_user_id).

Настройки окружения архива читаются через os.getenv; сам архив не содержит
runtime-значений токенов и адреса шлюза в изученных клиентах. Их нужно задать
на сервере. Отправка реальным клиентам при разработке не выполнялась.

При необходимости пути адаптеров можно переопределить через
`KARION_TELEGRAM_NOTIFICATION_BACKEND` / `KARION_MAX_NOTIFICATION_BACKEND`.
Контракт функции: `send(*, recipient, message, idempotency_key)`, исключение при
неподтверждённой отправке, нормальный возврат только после успеха.

## Повторные попытки и ограничения доставки

`SubscriptionReminder` хранит одну запись на пару подписка/дата окончания,
канал, число попыток, время успеха, тип ошибки и статус. До сетевого запроса
атомарный условный UPDATE переводит запись в `sending`: второй процесс,
использующий ту же БД, не может отправить эту запись повторно, даже без flock.
Файловая блокировка команды остаётся дополнительной локальной защитой.
Все отправители должны вызывать send_subscription_reminder, а не deliver_reminder.

- `sent`: повторная отправка для той же даты запрещена.
- `failed`: подтверждено, что отправка не выполнена (ошибка настройки,
  SMTP-отказ, HTTP 4xx кроме 408); можно повторить следующим запуском.
- `uncertain`: сообщение могло быть принято (read timeout, разрыв SMTP,
  HTTP 5xx, неизвестный ответ). Автоматически НЕ повторяется.
- `sending` после падения процесса: также НЕ повторяется автоматически.
- `skipped`: после захвата записи дата/состояние изменились, запроса не было.

`uncertain` и зависшее `sending` требуют проверки журнала провайдера оператором.
Только после подтверждения отсутствия доставки можно вручную перевести запись
в `failed`; если принятие подтверждено — в `sent` с фактическим sent_at.
Изменение канала не сбрасывает неизвестный результат старой попытки.
Автоматического сброса по времени нет: это могло бы повторить принятое сообщение.
Контакты и ответы шлюза в журнал ошибок не записываются. Ошибки, отсутствие
профиля и needs_review дают ненулевой exit status, не останавливая другие подписки.

Миграция 0027 добавляет только статус журнала: прежние успешные записи становятся
`sent`, прежние попытки без sent_at — `uncertain`, нетронутые — `pending`.
Контакты, сроки, платежи и Remnawave миграция не меняет. Для отката сначала
отключите планировщик: старый код не учитывает `uncertain`/`sending`.

SMTP использует SSL/465, а не STARTTLS. Одновременные SSL и TLS, отсутствие
логина/пароля и некорректный адрес блокируются до отправки. Ошибки не подавляются.
SMTPAuthenticationError, SMTPRecipientsRefused, SMTPSenderRefused и SMTPDataError
считаются отказами; неопределённый разрыв соединения — `uncertain`.
Резервной отправки другим каналом нет.

Дата перечитывается после захвата права отправки. Если она изменилась до запроса,
сообщение отменяется. Изменение во время HTTP/SMTP невозможно атомарно отменить:
успешная попытка фиксируется для старой даты, команда показывает sent_date_changed,
новый срок подписки остаётся без изменений. Для новой даты действует отдельная запись.
Строгая exactly-once доставка не гарантируется без идемпотентности провайдера;
цель состояний — не повторять автоматически неопределённые результаты.
Ручной повтор без проверки может создать дубль. idempotency_key не отправляется
недокументированным параметром шлюзу.
